采购申请示例 · 模块与实现待核实

项目整体介绍

一分钟口述稿

我在汉得主要参与企业 ERP 管理系统的后端功能迭代，使用 Spring Boot、MyBatis 和 MySQL。

按这版业务场景，我负责的是采购申请单管理相关接口，包括申请单列表、详情、新增和修改，以及提交时的状态校验。另外配合做了物料选择的数据查询，供前端填写申请明细。

这类单据分为主表和明细表。主表保存申请部门、申请人、申请日期、状态等信息，明细保存物料、申请数量、单位和需求日期。我主要处理接口参数、Service 业务逻辑和 Mapper SQL，再与 Vue 页面联调。

这部分工作里，我重点关注两个问题：一个是主表和明细保存时的一致性，以及单据提交后的修改限制；另一个是主从表关联查询时，分页条数和总数不准确的问题。

“按这版业务场景”是练习时的提醒，正式面试不能以这句话替代真实性确认。核实真实模块后，直接讲模块名即可。

面试官让你再讲详细一点

业务流程是使用者先填写申请部门、申请日期等头信息，再选择物料、输入数量和需求日期，保存为草稿。草稿允许修改，提交前检查必填信息和明细完整性，提交后进入后续处理，不能再通过普通编辑接口直接改内容。

我的工作范围集中在这些页面对应的后端接口，以及字段、状态、查询条件和错误提示的联调。后续采购下单、入库、财务处理和审批引擎不属于这版稿子的负责范围。

负责的业务模块

主要模块 采购申请单管理

按一条完整但有限的链路组织经历：

  • 列表：按单号、部门、日期、状态等条件查申请单，支持分页。
  • 详情：返回申请单头信息和明细，供查看或编辑。
  • 新增与修改：校验数据，保存主表和明细；只有允许编辑的状态才能修改。
  • 提交：检查单据状态和必要数据，执行合法状态转换。

采购申请表示内部提出采购需求，不能直接说成已经创建采购订单或完成入库。模块实际叫什么、状态怎样流转，需要以真实系统为准。

配套功能 物料基础资料查询

仅负责申请页面需要的查询：根据物料编码或名称搜索可选物料，返回编码、名称、规格和单位等字段。不要把一个选择器查询扩大成负责整套物料主数据系统。

数据关系的口述

主表对应一张申请单，一张单据有多条明细。明细通过主表 ID 关联，物料 ID 关联已有的物料资料。查询列表时，业务上分页的对象是单据；查看详情时，才需要展开整张单据的明细。

是否保存物料名称、规格等历史快照要看真实数据模型，不能自动说历史单据始终展示主数据的当前值。

六个具体接口怎么讲

接口示例 输入与输出 主要后端工作
GET /erp/purchase-requisitions 输入单号、部门、日期范围、状态、页码；返回单据列表与总数 拼接筛选条件，按单据分页，保证总数与列表采用相同条件

POST /erp/purchase-requisitions 输入申请头信息和明细；返回新单据 ID 校验必填信息、物料和数量，在同一事务中保存主表与明细
PUT /erp/purchase-requisitions/{id} 输入单据 ID 和修改内容；返回处理结果 校验当前状态，保证主表与明细一起修改，避免绕过状态限制
POST /erp/purchase-requisitions/{id}/submit 输入单据 ID；返回提交结果 校验操作权限、合法状态和必要数据，按条件更新状态并检查影响行数
GET /erp/materials/options 输入搜索词与分页参数；返回物料候选项 查询符合选择规则的物料，统一返回 ID、编码、名称、规格、单位等字段

最值得展开的接口 保存申请单

以新增申请单为例，前端传过来的是一份头信息和一个明细列表。我先做必填和格式校验，再由业务层检查物料是否允许选择、数量是否符合业务规则。然后保存主表，取得主表 ID，再保存关联的明细。主表和明细要一起成功，不能接口返回失败后，数据库里却留下半张单据。

联调时，我会核对主表和明细的关联是否正确，详情接口能否完整回显，再用无明细、非法数量、无效物料和中途失败这些情况检查处理结果。

申请人和部门信息的可信来源应遵循现有身份与组织权限规则，不能让前端随意指定后就直接写入。

修改明细为什么要多想一步

如果草稿明细没有被其他业务引用，且业务允许整单覆盖，可在同一事务中按现有方案替换明细。已有下游引用、行级历史或审计要求时，需要保留明细身份，逐行处理增删改。不要把“先删除全部明细再插入”说成所有 ERP 都适用的办法。

把经历讲完整的两分钟练习稿

下面整段仅在模块和实现得到核实后使用；核实前用来检查自己是否能解释每一句。

我在汉得主要参与面向企业的 ERP 系统后端开发，技术栈是 Spring Boot、MyBatis 和 MySQL。负责范围主要是采购申请单管理，以及申请页面需要的物料基础资料查询。

采购申请单这块，我参与了列表、详情、新增修改和提交相关接口。列表可以按单号、部门、日期和状态查询；新增修改需要处理单据头和多条物料明细；提交时需要检查当前状态和必要数据。我也配合 Vue 页面做联调，核对字段、状态值、日期和错误提示。

这段工作里，我主要能展开两个问题。第一个是主从表保存的一致性。单据头和明细应当一起成功，所以我关注 Service 层事务、异常处理，以及修改和提交的状态约束，避免留下不完整单据，或者提交后仍被编辑。

第二个是列表分页。因为一张单据有多条明细，直接关联后分页可能使单据重复，页面条数和总数也不一致。我的处理思路是先确认分页对象是单据，再选择主表筛选和分页方式，让列表与总数采用一致的条件，需要的明细按本页数据批量补充。

我负责的重点是具体业务接口、联调和问题排查。遇到问题时，会沿着请求参数、业务逻辑、SQL 和数据库数据定位，修改后验证原来的异常流程。这段经历让我更关注接口是否真正符合业务规则，以及数据最终是否正确。

两个难点追问

重点练事务回滚、重复提交、前端去重与 DISTINCT。这里是场景方案，确认符合实际后再用于经历表达。

先试着回答，再点题目看参考。

难点一 主从表保存和状态变更的一致性

七十至九十秒口述稿

第一个可以展开的难点是，申请单不是只写一张表。头信息和多条明细要一起保存，还要受单据状态限制。

这个问题可以用一个具体异常来说明：主表已经保存，但某条明细写入失败。如果处理不完整，就可能留下只有头信息、没有完整明细的单据。

我在处理这类接口时，会把主表和明细的数据库修改放进同一个 Service 事务里，在写入前完成必要的业务校验。执行中出现需要回滚的异常，就让异常按约定向外抛出，不把它捕获后直接返回成功。

对修改和提交，还要校验状态。比如只有草稿允许编辑，提交时把原状态放进更新条件，并检查影响行数。这样就不会仅凭页面按钮是否可点击来决定后端能不能操作。

验证时，我会分别检查正常保存、明细失败、提交后再编辑和重复提交。重点是确认数据库里没有半张单据，禁止的操作没有改变数据。

本段描述的是待核实的问题与方案，没有已确认的故障发生记录或回归结果。确认后才可改成“当时发现”“修复后验证”。

事务和重复提交的十二道追问

以下回答按普通同步方法、MySQL InnoDB 和 Spring 常见代理式事务讨论；具体经历与项目配置仍以真实系统为准。通常先说引用段落，被追问后再补解释。

01为什么把事务放在 Service 层

因为“保存一张申请单”是一个完整业务动作，里面可能要写主表和多条明细。我希望它们一起成功、一起失败，所以在处理这件事的 Service 方法上定义事务。只给单条数据库操作加事务，不能保证整张单据完整。

02什么异常会回滚 所有异常都会吗

不是所有异常都会。没有自定义规则时，Spring 默认对 RuntimeException 和 Error 回滚，受检异常默认不回滚。如果这个业务遇到某类受检异常也必须撤销，就要配置相应的 rollbackFor，不能只看见注解就认为肯定回滚。

参考：Spring 6.1 Transactional 注解说明。不同版本或项目全局配置可能改变默认规则，回答时说明“默认配置”。

03我把异常 catch 住 然后返回失败 会不会回滚

不能只看返回值写的是成功还是失败。比如我在事务方法里自己 catch 了异常，没有再抛出去，也没有其他回滚标记，事务通常还是会正常提交。接口虽然返回失败，前面已经写进去的主表却可能留下来。

我的处理方式通常是让需要回滚的异常按规则离开事务方法，再在外层统一转换成错误响应。

如果面试官继续追问，补一句：

但也不能说“只要 catch 就一定不回滚”。如果异常已经经过内层事务代理，把共同事务标成只能回滚，外层再 catch 也不能恢复提交，最后还可能遇到 UnexpectedRollbackException。

第一种情况是自己捕获后事务没有收到回滚信号；第二种情况是事务已经被标记回滚。Spring 回滚说明、事务传播说明

04那全局异常处理器捕获异常 会不会影响回滚

一般不会。常见调用顺序是 Controller 调用事务 Service，异常先从 Service 出来，由事务代理处理回滚，然后再交给全局异常处理器组织响应。关键是捕获发生在哪一层，不能把“事务方法里自己吞掉”和“事务外统一处理”混为一谈。

05加了 Transactional 还是没回滚 你先查什么

我先看这次调用有没有真的经过 Spring 的事务代理，比如是不是同一个类里直接调用了带注解的方法。再看异常有没有被自己捕获、是否符合回滚规则，以及主表和明细有没有参加同一个事务。最后核对有没有新线程、独立事务或提前提交的操作。

补充：同类自调用不会单凭被调用方法的注解新增事务；如果外层本来已经有事务，内部 SQL 仍可能参与外层事务，不能说自调用就使所有 SQL 都没有事务。Spring 代理式事务说明

06写上 rollbackFor 等于解决全部回滚问题吗

不等于。它只是告诉 Spring，哪些异常离开事务方法时应该触发回滚。调用没经过代理、异常被自己捕获、SQL 不在同一个事务里，这些问题都不是加一个 rollbackFor 就能解决的。

也不必把所有业务方法都机械配置为回滚所有异常，应遵循业务和团队约定。

07有事务了 为什么还要防重复提交

事务管的是“一次操作里的几步要不要一起成功”，重复提交管的是“同一件业务会不会被做两次”。两个请求各自都可以有事务，也都成功，所以有事务不代表自动防重。

可以举例：两次新增请求分别创建两张完整单据，每张主表和明细都没有问题，但业务上仍然重复了。

08同一张草稿单据被点了两次提交 你怎么处理

前端禁用按钮可以减少误操作，后端还要有约束。我会把“当前状态必须是草稿”放进更新条件，而不是先在 Java 里查到草稿，再无条件修改。一次更新成功后，另一次就不能再按草稿提交。

然后检查影响行数。只有拿到这次状态转换的请求，才能继续做同一事务内的后续写入。第二次是返回状态冲突，还是返回前一次的结果，要看接口约定，关键是不能再做一遍业务动作。

这里保护的是这一次状态转换；如果单据允许撤回后重新提交，还需要识别是哪一轮操作。数据库之外的审批通知或 HTTP 调用，也不能单靠这条更新和本地事务保证一致。

继续追问“编辑和提交同时发生”时：

这两个接口需要遵循同一套并发规则，不能只保护提交。比如在事务内锁定单据头、检查状态后再修改明细，让提交与编辑按同一记录协调；或者使用版本校验，冲突时撤销整次修改。这样才能避免提交完成后，一个旧编辑请求又改了明细。

以上是备选方案，未核实实际实现前不说“项目已经这样做了”。

09如果是重复新增 两次都还没有单据 ID 呢

这时就不能靠单据当前状态拦了。我会先确认什么算同一笔业务。如果有稳定的业务唯一键，就用它做唯一约束；没有的话，可以给这次新增操作分配一个幂等标识，重试时沿用它，再用数据库唯一约束挡住并发重复创建。

这个标识要和用户、业务范围对应起来。同一个标识带了不同内容，不能直接当成同一次成功。重复请求返回已有结果，还是提示冲突，也要先定义清楚。

“先查一下有没有再插入”仍有并发空隙；不能用每次都新生成的单号识别同一次业务重试。

10为什么不直接用 Redis 锁

先看问题大小。如果只是同一张单据从草稿变提交，数据库条件更新可能就够了，没必要为了防重再加一套锁。Redis 可以帮助拦短时间的重复请求，但还要处理过期和中途失败，重要的业务结果仍要靠持久化规则保证。

Redis 锁不是不能用，而是不能把“拿到锁”当成“整笔业务已经正确完成”。

11请求超时能不能直接再提交一次 事务会自动撤销吗

超时只说明调用方没及时收到结果，不能证明服务端没保存。可能服务端已经提交成功，只是响应没有回来。我会先按单据号或幂等标识查结果，再按接口约定重试，而不是换个新标识再创建一张。

数据库事务也不能撤销已经成功的外部 HTTP 操作，所以调用外部系统时，还需要考虑结果确认和对账。

12你怎么验证真的回滚了 真的防重了

回滚不能只看接口报了错。我会让主表写入后、明细写入过程中出现一个可控失败，再直接查数据库，确认本次主表和已经写入的明细都没有留下。修改场景还要确认旧数据保留完整。

防重则用同一个业务标识发重复请求，包括同时发两个请求，最后确认只有一笔业务结果，状态和相关记录都没有重复。再确认失败后重试能够按设计处理，而不是被一个永久的“处理中”标记卡住。

这是建议的验证方式，不表示已经在汉得项目执行过这些检查。

难点二 主从表关联导致分页与总数不准

七十至九十秒口述稿

第二个难点是列表查询的分页单位。页面要展示的是申请单，但一张申请单下面可能有多条物料明细。

如果为了支持按物料筛选，直接把主表和明细表关联后分页，同一张单据可能占多行。这样 SQL 返回十行，页面去重后可能只剩几张单据，总数也容易按明细行数统计，和用户看到的不一致。

我会先用一张有多条明细的申请单复现，对照原始 SQL 结果和页面结果，确认分页发生在关联展开之后。

解决时，先明确列表以单据为单位。如果只是判断单据里有没有某种物料，可以用存在性条件筛选主表，再对主表分页；列表查询和总数查询使用相同的业务筛选。如果还需要补充明细摘要，就针对本页单据统一查询并组装，避免每张单据再单独查一次。

最后检查一单多行、跨页、无结果和物料筛选这些情况，确认条数与总数符合“单据”的含义。

本段同样是候选故事。没有确认真实发生过，就用“这种场景我会这样处理”回答，而不是声称已修复公司故障。

分页和去重的八道追问

01为什么一关联明细 分页就不准了

因为页面的一条数据是一张单据，但 SQL 关联之后的一行可能只是这张单据的一条明细。一张单据有三条明细，就可能变成三行。直接对这个结果分页，分页的单位就从“单据”变成了“关联后的行”。

关键不是 JOIN 本身有问题，而是查询结果的单位和页面需要的单位不一致。

02返回前端后 按单据 ID 去重不就行了吗

如果后端已经分页了，前端只能去掉这页里的重复项，补不回来其他单据。比如 A 单有三条明细，B 单有一条，后端先取三行，拿到的可能全是 A。前端去重后只剩一张单据，却拿不到本来应该展示的 B。A 还可能跨到下一页，总数也仍然是错的。

用四行数据就能讲清：

单据 ID 明细 ID
A A1
A A2
A A3
B B1

如果每页需要两张单据，期望第一页是 A、B；对关联结果先取两行再去重，只能得到 A。

03那我直接在 SQL 加 DISTINCT 呢

可以考虑，但先看选了哪些字段。DISTINCT 去掉的是“所选字段都相同”的行，不是默认按单据 ID 去重。如果只选主表的 ID、单号等字段，它可能就能解决；如果还选了明细 ID、物料和数量，每条明细本来就不同，加了也不会合并成一张单据。

所以我不会说 DISTINCT 一定不能用，而是先确认返回结果里一行究竟代表什么。

例如 A, A1 和 A, A2 是不同的两行；只选择单据 ID 时，两行才都是 A。同一层查询中，按正确主表字段 DISTINCT 后再 LIMIT 是可行方案，不能误说“DISTINCT 永远在分页之后，所以没用”。MySQL DISTINCT 与 LIMIT 说明

04列表加 DISTINCT 总数用 COUNT DISTINCT 就全部解决了吗

如果列表确实已经做到一张单据一行，总数也按同样筛选统计不同单据，这是一种可行方案。但只把总数改正确，列表还在按明细分页，仍然会出现一页条数不够的问题。另外，权限、物料和日期这些筛选，两边都要一致。

统计主表可直接按主表条件计数；保留会展开明细的关联查询时，可以按实际需要统计不同主表 ID，不能机械地把所有查询都改成 COUNT DISTINCT。

05你最后会选什么查询方式 为什么提到 EXISTS

如果页面只要求“查出包含某种物料的单据”，我会考虑在主表查询里加 EXISTS，判断有没有符合条件的明细，而不是把所有明细都展开。这样筛选完成后，一行还是一张单据，再分页就比较直接。

这是因为它符合业务含义，不是因为 EXISTS 一定比 JOIN 快。性能还要看 SQL、索引和执行计划。

还要明确多个明细条件是否必须落在同一条明细上。例如“物料 X 且数量大于十”，通常需要同一条明细同时满足，不能误写成两条不同明细分别满足。

06能不能先对主表分页 再筛选明细

如果明细只用于展示，可以先分页，再补充明细。但如果用户按物料筛选，就要在确定这一页单据之前应用这个筛选。不能先取十张单据，再把不符合物料条件的删掉，否则符合条件的其他单据没机会进来，总数也对不上。

记住顺序：先按全部业务条件确定符合条件的单据，再对单据分页，最后补页面需要的展示数据。它是业务处理顺序，不是数据库执行计划的承诺。

07这一页还要显示明细 怎么查比较合适

我会拿到这一页的单据 ID 后，批量查需要的明细，再按单据 ID 分组组装。不要循环十张单据再分别查十次，查询次数会跟着页大小增长。

另外要和前端确认，是展示整张单据的明细，还是只展示命中筛选的明细。比如按物料 X 查到一张单据，并不代表详情里只能显示 X，这两个含义不能混在一起。

08怎么保证翻页稳定 怎么验证改好了

排序不能只依赖一个可能重复的时间字段，可以再加唯一 ID 形成明确顺序。验证时准备一张多明细单据和几张普通单据，检查每页单据数、跨页重复、总数，以及物料筛选后是否漏单。

不过排序稳定不等于多次请求之间数据完全不变。有人持续新增、删除时，偏移分页仍可能受影响；是否需要游标或快照，要看实际需求，不在这次问题里直接扩大改造。

05一次请求从页面到数据库经过什么

**追问：**参数合法但当前状态不允许操作，应该在哪里判断？通常属于业务规则，放在业务层，并用数据库条件保证修改时规则仍成立。

06查询接口你一般会注意什么

先明确可用筛选项、分页和排序规则，再处理参数绑定与 SQL。查询结果和总数应该遵循相同的业务筛选，排序尽量稳定。联调时验证无结果、多页、日期边界和非法排序字段；如果响应慢，再看 SQL、执行计划及数据量，而不是先上缓存。

**追问：**为什么翻页出现重复记录？可能是排序字段不唯一、期间数据变化或分页逻辑问题，要根据实际查询确定。

07MyBatis 的井号和美元参数有什么区别

#{}通常通过预编译参数绑定传值；${}做字符串替换。普通值参数用前者。动态列名、排序方向不能直接相信用户输入，要映射到服务端允许的选项。MyBatis 官方说明解释了参数绑定和字符串替换的区别。

**追问：**排序列能不能写成 ORDER BY #{column}？这不会把绑定值当作列标识符使用，应当用白名单映射到已知列。

08Spring 事务什么时候不生效

先看调用是否经过 Spring 事务代理。同类内部直接调用带注解方法，在默认代理模式下不会因此新开启事务。再看异常是否抛出、回滚规则、事务管理器和线程边界。默认通常对运行时异常和 Error 回滚，受检异常需看配置。不能简单说“所有非 public 方法都不支持”，还要看代理方式与版本。Spring 事务文档

**追问：**数据库事务能回滚已经发出的 HTTP 请求吗？不能，跨系统要单独处理失败、幂等和结果确认。

09单据重复提交怎么办

先分清两种情况：重复提交同一张单据，可以用合法状态条件限制转换；重复创建业务单据，需要稳定的业务键或幂等键，并用数据库唯一约束保证持久化结果。前端禁用按钮能改善体验，后端仍要保护数据规则。

**追问：**为什么先查有没有再插入不够？两个并发请求可能都查到不存在，需要数据库约束或相应并发控制保证最终结果。

10库存扣减怎么避免负数

这是场景方案：在适合的模型下，用带数量条件的原子更新扣减库存，再检查影响行数；关联出库单和流水放在同一数据库事务中，并控制同一业务重复扣减。若规则要求先读再改，可在事务内考虑锁定读取，但要明确索引、锁范围和竞争成本。MySQL 锁定读取文档

**追问：**加了事务为什么仍可能重复扣减？事务本身不代表业务幂等，重复业务请求仍需要识别。

11SQL 慢怎么排查

先确认慢在哪里：接口总耗时、数据库执行、锁等待还是外部调用。拿到具体 SQL 和参数，用 EXPLAIN 看访问路径、索引和预估扫描量，再结合实际数据分布检查过滤、排序、分页和关联。根据查询模式调整，不能看到慢就给每列加索引。

**追问：**为什么联合索引不是越多列越好？索引有空间和写入维护成本，字段顺序也要服务实际过滤和排序方式。

如果被问“能否用 Redis 防重复”，可以说短期标记能减少重复请求，但过期、失败和数据库写入之间仍有边界，重要业务还要有持久化幂等规则。SET支持条件写入和过期选项，但命令成功不代表整个业务事务完成。Redis SET 文档

**追问：**没有请求 ID 怎么查？用准确时间、接口、允许记录的业务标识缩小范围，不凭空声称原系统已经有全链路追踪。

15ERP 和 MES 对接超时能直接重试吗

**追问：**如何处理重复回调？在确认业务唯一范围后，对事件标识做持久化去重，业务效果和处理记录需要保持一致。

16客户说一个按钮做完所有操作怎么办

先让客户举一个完整业务例子，再确认按钮背后的状态变化、权限和失败处理。例如“提交”是否意味着进入审核，还是已经影响库存和财务？把正常流程、例外规则和验收条件写清楚，再拆成可交付的范围。不能把一句界面描述直接当成完整需求。

两个 ERP 场景练习

以下表名、字段和状态完全是练习示例，与汉得真实数据库无关。重点练说明规则，不要求背 SQL。

场景一 把草稿单据改为已提交

前提：请求已通过操作权限和数据范围校验，示例单据允许从草稿进入已提交。

UPDATE business_document
SET status = 'SUBMITTED', updated_at = CURRENT_TIMESTAMP
WHERE id = :documentId AND status = 'DRAFT';

面试口述：更新条件同时限制单据和原状态，检查影响行数，避免把任意状态直接覆盖。真实系统还要依据权限模型加入相应限制；同一事务中的业务记录也要一起成功。影响零行不能直接返回操作成功。

再问自己：单据撤回后是否可以重新提交？第二次提交是重复请求还是新的业务动作？这说明幂等键要按业务生命周期设计，不能机械地把单据 ID 永久当成唯一提交次数。

场景二 同一出库业务不能重复扣库存

前提：quantity为已校验的正数，库存行由主键定位，数量精度符合业务规则。

UPDATE inventory
SET available_qty = available_qty - :quantity
WHERE id = :inventoryId AND available_qty >= :quantity;

面试口述：条件更新保护单行可用库存不被扣成负数；影响一行才能继续确认扣减成功。它没有独自解决业务重复、跨行分配、预占库存和外部系统一致性。出库单、库存流水和幂等标识应按业务设计，并保证相应本地修改处于一致的事务边界。

不用主动声称写过这段代码。被问“如果让你做”时，它才是场景方案。

补充与核实

汉得到底做了什么

可以直接使用的职责描述

我在汉得主要参与企业 ERP 管理系统的后端开发，技术栈是 Spring Boot、MyBatis 和 MySQL。具体工作包括业务数据查询、状态更新接口、请求参数校验，以及配合前端完成联调。发现问题后，我会结合浏览器请求、数据库数据和 Linux 日志定位，修复后回归相关流程，同时整理接口说明和修改记录。我也接触过 Vue 页面，所以能从请求发出到后端处理、数据库变化这一整条链路看问题。

这段以简历和本次补充为依据。它已经能回答“做了什么”，下一步要补的是一个自己能解释清楚的接口。

把日常工作拆成五件具体事

  1. 看懂需求。 明确页面要展示什么、接口接收什么、数据从哪里来、哪些条件下允许修改。
  2. 写查询接口。 处理筛选条件、分页、返回字段和 MyBatis SQL，保证页面结果与数据库一致。
  3. 写修改接口。 处理参数和业务规则校验，更新数据并返回明确结果。多表同时修改时需要考虑事务。
  4. 完成联调。 对齐字段名、类型、日期格式、状态值和错误提示，检查接口响应与页面展示。
  5. 排查与回归。 留下复现条件，查请求、SQL 和日志，修复后验证正常流程和原来的异常流程。

其中“分页”“多表事务”等是常见工作细化点，需与你实际做过的接口核对，不能仅因 ERP 常见就认定都做过。

面试官问具体负责哪个模块

优先找回一个真实名称：可以回看自己合法保留的工作记录、接口文档或非敏感提交记录，不需要拿原公司的内部数据做面试展示。

暂时想不起来时，练习中先用“业务单据查询和状态更新”作为中性名称。这个名称只用于组织思路；它不是已经确认的采购、库存或审批模块。

可以坦诚说：

我主要负责其中的业务查询和状态更新接口，不是整个 ERP 的架构设计。具体页面名称我现在记得不够准确，但接口从参数、Service 逻辑、Mapper SQL 到联调验证这条链路，我可以展开讲。

不必用“保密”掩盖记忆空缺。也不要因为汉得做企业服务，就自动说自己做过 SAP、Oracle、某个自研平台或 MES。

选一个接口讲完整

按这六项准备，选真实做过的一条：

项目 要能回答的问题
使用者 谁在什么页面、什么情况下调用？
输入 哪些筛选或修改字段，哪些必填？
规则 什么身份能操作，什么状态允许修改？
实现 Controller、Service、Mapper 分别处理什么？
数据 查或改了哪些数据，多表关系如何处理？
验证 正常请求、非法参数、重复操作怎么验证？

如果有三项以上说不清，先换一个更熟悉的接口，不要再往里面堆缓存、消息队列和分布式锁。

公司项目中难忘的点

下面三段都是候选故事。它们紧贴简历中的查询、状态更新和联调，但具体故障、方案和结果仍需你确认。可以用来唤起记忆；不符合真实经历的，改成“如果遇到，我会这样处理”的场景回答。

候选故事一 查询有结果却漏了最后一天的数据

**适用前提：**你确实接触过日期筛选或前后端日期格式问题。

练习口述：

有个让我印象比较深的点，是业务列表的日期筛选。页面能正常查询，接口也没有报错，但用户选择一个时间范围时，结束日期当天的数据没有完整展示。

我会先固定一条漏掉的记录，核对前端实际传的日期、后端接收到的参数和数据库里的时间，再看 SQL 边界。如果结束日期被处理成当天零点，就可能漏掉当天后面的记录。

对于按自然日查询的需求，可以在明确业务时区后，把条件处理成“大于等于开始日零点，小于结束日下一天零点”，再验证结束日白天和临近午夜的数据。

这个问题让我意识到，接口返回成功还不够，筛选条件必须和业务含义一致。

当前用“我会”表达方案；确实回忆起发生过，再把有依据的部分改成过去时。

**可能追问：**为什么不用当天 23:59:59？因为数据库时间可能含小数秒，半开区间更容易明确边界；还要确认业务日期、存储时区和转换规则。

**需要确认：**实际日期字段是什么，漏数是否真的发生，自己改的是前端参数还是后端 SQL，最后验证过哪些记录。

候选故事二 状态更新不能只靠页面按钮控制

**适用前提：**你确实接触过提交、撤回、审核或其他状态修改接口。

练习口述：

状态更新这类接口让我印象比较深。表面上只是改一个字段，但背后有“什么状态允许操作”的业务规则。即使前端已经把按钮禁用了，后端也不能直接相信请求。

如果处理单据提交，我会先核对操作权限和合法状态，再把原状态放进更新条件。比如只允许草稿提交，就用“单据 ID 加当前状态是草稿”作为条件，然后检查实际影响行数，避免两个请求都按照旧状态继续执行。

如果同时更新主表、明细或业务记录，还需要把应当一起成功的数据库修改放在同一个事务中，失败时保持数据一致。

这个点让我更关注接口对业务规则的保护，而不只是数据能不能写进去。

**可能追问：**更新零行是什么原因？可能是记录不存在、状态已变化，也可能是数据权限不匹配。返回什么错误要遵循系统的权限和信息披露规则，不能一律报成功。

**需要确认：**真实状态有哪些，是否写过条件更新，是否存在多表修改。未做过事务或幂等，不补成个人成果。

候选故事三 联调时从页面现象追到接口和 SQL

**适用前提：**你确实排查过字段、状态或接口返回与页面不一致的问题。

练习口述：

我印象比较深的是联调问题不能只看页面现象。比如页面显示的状态不符合预期，我会先在浏览器 Network 里看实际响应，确认后端返回的是编码、名称还是空值，再核对前端映射。

如果响应本身不对，就继续检查请求参数、Service 分支、SQL 和数据库数据。这样可以先把问题缩小到前端展示、接口映射还是数据处理，不用两边同时猜。

确定原因后，把字段含义、空值和状态值的约定补清楚，修改后重走同一条流程。

这段经历可以突出我虽然主要做后端，但能够沿着前后端链路定位问题。

**可能追问：**HTTP 200 就代表业务成功吗？不一定，要看约定的业务结果；还要核对实际影响行数和最终数据，不能把“请求到了”当成“操作成功”。

**需要确认：**当时具体是哪一个字段，根因在前端还是后端，自己负责了哪一步。结果没有记录时，不写“减少 80% 问题”等数字。

怎么选择两个最合适的故事

优先选择能回忆起“页面或接口、具体异常、自己做的修改、验证方式”的两段。只记得一般联调工作，就先讲第三段的排查方法；不要为显得复杂硬讲生产事故。

结果可以是“日期边界符合预期”“重复请求没有再次改变状态”“字段约定明确后联调通过”。只有真实确认后才使用过去时。

面试前只核实这几项

  1. 实际模块是否是采购申请；如果不是，把业务名换回真实模块，并重新核对操作和状态，不能只替换名词。
  2. 是否亲自做过新增修改、主从表事务和提交接口；只做过查询，就保留查询职责，把修改方案作为知识题准备。
  3. 两个难点是否真实发生过，自己的具体修改和验证是什么。能解释方案不等于有过这次故障经历。

正式回答优先讲清一条真实接口和一个真实问题；另一个没有确认的难点可以作为场景题练习，不必强行凑成两次过去业绩。

具体模块与故障为待核实示例；场景方案不代表已经完成的工作。
